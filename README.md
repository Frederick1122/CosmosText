# CosmoTextGame

Текстовая survival-RPG на телефон, сеттинг — космос. Дизайн-документы (`gdd-v1.md`, `tech-spec-v1.md`) живут в Claude-проекте «CosmoTextGame», не в этом репозитории — здесь только код и контент.

## Открыть и сыграть

1. Godot **4.7** (`config/features` в `project.godot` зафиксирован на "4.7" — под конкретно установленную у тебя версию 4.7.2).
2. Godot → Import → указать эту папку → Import & Edit.
3. F5 (или Run) — main scene теперь `scenes/Game.tscn`, простой, но полноценно играбельный UI: главное меню → карта сектора → ситуации/бой → экран смерти. Кнопка "Архив" вверху — открытые лор-фрагменты, доступна в любой момент.

`scenes/Main.tscn` (без UI, только печать в Output) оставлен отдельно как регрессионный смоук-тест — можно запускать его вручную (F6) при подозрении, что сломалась логика, а не отрисовка.

## Важно про эту версию

Код я писал вручную в облачной песочнице — она даёт мне только headless Godot **3.5.2** через apt, скачать бинарник Godot 4 сетевая политика не пускает. Значит: сам я этот Godot-4-проект не запускал и не отлаживал в редакторе, в том числе UI из `scenes/Game.gd`. Что я всё же проверил здесь автоматически:

- JSON-контент (`data/**/*.json`) — валиден и не содержит битых перекрёстных ссылок: прогнан `tools/validate_content.py`, 0 ошибок.
- Все `.gd`-файлы — сбалансированные скобки, единообразные отступы (табы). Не замена парсеру GDScript, но ловит самые грубые опечатки.
- `Game.gd` собран из простых Control-нод программно (Label/Button/VBoxContainer/ScrollContainer), без ручного `.tscn`-разметки — минимизирует риск битых anchor/layout свойств, которые я не могу проверить глазами без редактора.

Реальная проверка — запустить `Game.tscn` у себя и пройти вертикальный срез целиком: меню → карта → грузовой отсек → бой → возврат на карту → хаб (чекпоинт) → намеренная смерть → экран смерти. Если что-то падает или выглядит не так — кидай мне текст ошибки или скриншот, поправлю в следующей итерации.

## Структура

```
project.godot            — конфиг движка, автозагрузки, portrait 1080x1920, main scene = scenes/Game.tscn
autoload/                 — 11 систем-синглтонов (см. tech-spec-v1.md)
data/                     — весь контент отдельно от кода
  config.json             — баланс: слоты инвентаря, стартовые HP/O2/ammo
  items.json              — справочник предметов
  enemies.json            — справочник врагов + спец-действия в бою
  lore.json               — тексты лор-фрагментов (Archive)
  situations/*.json       — по одному файлу на ситуацию
  sectors/*.json          — узловые карты секторов
scenes/Game.gd|.tscn      — playable UI (единственная реальная сцена игры)
scenes/Main.gd|.tscn      — служебный смоук-тест без UI, печать в Output
tools/validate_content.py — офлайн-валидатор ссылок в JSON-контенте
```

## Что реализовано (по tech-spec-v1.md)

Все 10 систем из ТЗ + `EffectResolver` (см. отклонения ниже) + простой UI поверх них:

- EventBus, ResourceSystem (HP/O2/ammo), InventorySystem (6 слотов), ArchiveSystem,
  MapSystem, SituationEngine, CombatSystem, EconomyManager (mock-провайдер),
  SaveManager (run/meta/checkpoint), GameState (FSM экранов).
- `scenes/Game.gd` — один экран, который целиком перерисовывается при смене `GameState.current_screen`: главное меню, карта, ситуация, бой (с динамическими кнопками спецдействий/предметов), экран смерти (restart/rollback), архив лора. HUD (HP/O2/патроны/инвентарь) — постоянная полоса сверху.

Контент вертикального среза: три ситуации из плейтест-скрипта GDD (раздел 9) — пробуждение → находка планшета → бой с дроном, один сектор `wreck_01` с узлами "хаб" и "грузовой отсек".

## Отклонения от tech-spec-v1.md (и почему)

1. **`EffectResolver`** — новый автозагруз, не описанный в исходном ТЗ. Ситуации и предметы используют одинаковую форму `effects`/`use_effect`; без общей точки применения пришлось бы дублировать switch по типу эффекта в `SituationEngine` и `InventorySystem`.
2. **Разделение "ситуация подхода" и "бой"** — бой (1.3) в GDD был единой ситуацией с боевыми опциями A/Б/В. В реализации это два объекта: `sit_1_3_drone.json` — только решение "войти в бой / отступить", сами боевые действия идут через `CombatSystem.player_action()`. Система боя переиспользуется для любого врага, а не хардкодится под одну сцену.
3. **Экран смерти решает сам** — `SaveManager` не выбирает restart/rollback при `player_died`, только сохраняет meta. Выбор — за игроком (`GameState.choose_restart()` / `.choose_rollback()`).

## Три реальные ошибки интеграции, найденные и исправленные при сборке UI

Не гипотетические — я прошёл логику руками шаг за шагом при подключении экранов и поймал три места, где системы из ТЗ не стыковались друг с другом:

1. **Дрона можно было "убить" повторно.** После победы `GameState` возвращал экран на `SITUATION`, а `sit_1_3_drone` — всё та же ситуация с опцией "войти в бой" внутри. Исправлено: у `CombatSystem` появилось поле `clear_node_id` (приходит из эффекта `start_combat.clear_node` в JSON), и по итогу боя `GameState` сам помечает узел карты "пройдено" (победа) или "опасно" (побег), а экран уходит на карту, не обратно в ситуацию.
2. **Откат к чекпоинту списывался дважды.** И `EconomyManager.watch_rollback_ad()`, и `SaveManager.confirm_rollback()` вызывали `use_rollback()` — при рекламном пути счётчик уходил в минус за один клик. Исправлено: `confirm_rollback()` больше не трогает экономику — списание происходит один раз, на стороне UI, по выбранному пути (платный/рекламный).
3. **O2 мог продолжать тикать на карте** — защитная правка, не баг, который проявился, а потенциальный: `GameState._set_screen()` теперь явно выключает тик O2 при переходе на экран карты, независимо от того, что было выставлено в предыдущей ситуации.

Это ровно то, ради чего я предупреждал — без запуска в реальном Godot 4 такие стыковки между модулями я не увижу, ловлю только то, что можно проверить чтением кода вручную.
